Yes—more actual specimens and construction material, fewer incident reports, and no padding the list with another ten Tetris forks.

I dug into three additional veins: **steganography**, demoscene-style playback, and custom viewers that extend what a PDF can contain. These add genuinely different mechanisms to the previous list.

Research date: 31 October 2026. These are source-backed leads, not executions I performed. I distinguish author-reported functionality from proposed experiments.

## 1. A secret message in the font mapping

[thoppe/PDF_steganography](https://github.com/thoppe/PDF_steganography)

This is a small, unusually approachable project: source, a Makefile, an example PDF, font-modification scripts and a presentation from DC Hack && Tell.

The author explicitly invites you to copy and paste the text to see the hidden information. The message lives in the font mapping rather than an obvious attachment. Its build uses pdfLaTeX and traditional font tools including `afm2tfm`, `tftopl`, `t1disasm` and `t1asm`.[1]

### Why it is worth dissecting

You get a concrete bridge between three things:

- What the glyph looks like.
- What character code the PDF uses.
- What text a consumer recovers.

The useful starting files are `example.tex`, `replace_sub.py`, `sub_cipher.py` and the Makefile. This is much closer to “take apart a little machine” than a large SDK.[1]

Proposed remix: a poem with a second poem revealed by copying it. Both readings should be intentional and artistically coherent.

Then test whether the second poem survives extraction, rewriting and printing. Do not assume it does.

Status: historical project; build compatibility and viewer behaviour need retesting. No licence was evident in the retrieved README.

## 2. PDF HIDE: a research prototype with samples and tests

[ncanceill/pdf_hide](https://github.com/ncanceill/pdf_hide)

This project grew out of University of Amsterdam research conducted in December 2012. It embeds and extracts data in text-containing PDFs, uses Python 3, and requires qpdf for compressed documents. The repository contains `sample/`, `test/`, the implementation, a changelog and a disclaimer. GPLv3-or-later.[2]

### Why it belongs in the workshop

Not because we should accept its README’s claim that only the recipient will suspect hidden content—that is an assertion, not a demonstrated guarantee.

It belongs because we can investigate:

> Which representational freedoms does the implementation use to carry information, and which transformations destroy that channel?

I have verified the project’s existence, documented dependencies and research origin, but have not inspected enough implementation code to make a precise claim about its encoding mechanism. That is a worthwhile next source-reading task.

Proposed experiment: embed an owned phrase such as “THE DOCUMENT HAS A CELLAR,” then compare survival through:

- A structure-preserving rewrite.
- Font changes.
- Rasterisation.
- OCR reconstruction.
- Print-to-PDF.

Score recoverability and visible change separately.

## 3. PDFStego: the hidden message that extraction immediately exposes

[aagallag/PDFStego](https://github.com/aagallag/PDFStego)

This 2016 C++ project uses PoDoFo. It encrypts a message with AES-128-GCM, Base64-encodes it, then embeds it in the PDF. The author gives an admirably clear warning: although viewers may not render the hidden text, ordinary extraction can reveal the encrypted material. GPLv3-or-later.[3]

### Why this is a better teaching specimen than “undetectable steganography”

It separates three properties people routinely confuse:

| Property | Question |
|---|---|
| Visual concealment | Does a person looking at the page notice it? |
| Discoverability | Can inspection or extraction reveal that something is there? |
| Confidentiality | Can someone read the recovered message without the key? |

The project demonstrates why these are different questions.[3]

Proposed artwork: a normal-looking letter whose extracted text contains an encrypted second letter. Give the key somewhere in the visible composition.

The “backdoor” is an intentional alternate reading—not a route into the reader’s device.

## 4. Bad Apple in PDF: the document as a playback engine

[esdmr/badpdf](https://github.com/esdmr/badpdf)

The author describes a “Bad Apple!!” playback experiment in a JavaScript-enabled PDF viewer and reports testing in Chromium/PDFium and Firefox/PDF.js. They warn that initial loading may take time. I could retrieve the search-indexed project description, but the full repository fetch failed. Consequently, I have not verified its detailed implementation or licence.[4]

### What to investigate rather than merely replay

- How are frames represented?
- How much changes per frame?
- What is the display primitive?
- Is timing driven by the viewer?
- How much of the file is playback logic versus frame data?

Those are open implementation questions here, not findings.

Proposed remix: a ten-second animation made from your own graphics, benchmarked across readers. Treat the PDF runtime as a constrained demo platform: file size, frame rate, loading time and fidelity all matter.

This is distinct from “embed a video player.” Establish the mechanism before putting it in either category.

## 5. Asymptote: the page contains a manipulable object

[Asymptote source](https://github.com/vectorgraphics/asymptote)  
[Author’s 2026 presentation](https://www.math.ualberta.ca/~bowman/talks/tug26.pdf)

Asymptote is a graphics language with a long history of embedding interactive 3D content in PDFs. Its tutorial describes PRC-based output that can be rotated in Adobe Reader. A 2026 presentation describes V3D as a newer representation, embeddable in PDFs and supported through dedicated viewer projects.[5][6]

### A concrete artefact to inspect

[Scott Pakin’s Blender → Asymptote → interactive PDF example](https://www.pakin.org/~scott/asymptote_export/blender_asymptote.pdf)

The example explains its own pipeline: Blender model, export script, Asymptote-generated PRC, then LaTeX embedding. In supported Adobe viewers it becomes interactive; other viewers show the static poster. That is the author’s historical compatibility statement, not a current universal rule.[7]

Proposed piece:

> A printed blueprint becomes a sculpture when opened in the right interpreter.

The interesting comparison is not just whether rotation works. Compare the static poster with the actual model: what geometry, labels or hidden surfaces exist in one representation but not the other?

## 6. `pdfv3dReader`: stop accepting the viewer as fixed

[vectorgraphics/pdfv3dReader](https://github.com/vectorgraphics/pdfv3dReader)

This is a JavaScript-based viewer for PDFs containing embedded V3D content. The repository uses PDF.js, Node.js and webpack, and links to the V3D specification and Asymptote as the generator.[8]

This opens a different creative route:

> Instead of only asking what current readers permit, build an explicitly named reader that interprets an additional layer.

Proposed experiment: one file, two experiences:

- Ordinary reader: a useful static illustration.
- V3D-aware reader: an interactive model.

The honest label matters: this is custom-reader functionality, not proof that ordinary PDF viewers support V3D.

That could become a separate PDF LAB track: experimental interpreters, with clear fallback behaviour.

## 7. Okular V3D plugins: real viewer surgery

[vectorgraphics/Okular-v3d-Plugins](https://github.com/vectorgraphics/Okular-v3d-Plugins)

This repository adds rotation, zooming and panning for V3D content, both standalone and embedded inside PDFs. The README says the models must be prerendered and the plugin must match the installed Okular version.[9]

### Why this is unusually useful reverse-engineering material

The documentation exposes the integration points:

- Recognising embedded content.
- Reading it from rich-media annotations.
- Tracking model locations on pages.
- Compositing rendered model images into the page.
- Handling interaction.

The PDF component modifies Okular’s existing Poppler-based plugin rather than inventing a complete PDF renderer.[9]

Proposed investigation: trace one owned model from embedded bytes to pixels. That is a concrete tour of where “PDF rendering” ends and viewer-specific interpretation begins.

Build burden is significant. Keep this off the first-demo critical path.

## 8. PoC||GTFO as a format-craft zine, not an exploit catalogue

[PoC||GTFO 0x04, June 2014](https://archive.org/details/pocorgtfo04)

This issue contains Ange Albertini’s articles on placing a TrueCrypt volume inside a PDF and adding ZIP “feelies” that Adobe tools recognise as legitimate attachments. Those are described in the issue’s own introduction.[10]

Why it is relevant: the publication is itself part of the experiment. The file’s physical construction participates in what the articles teach.

For PDF LAB, read this as format archaeology. Use harmless text archives when reproducing the structural ideas; legacy encrypted-volume tooling is not necessary.

Proposed editorial direction:

> Every lab report should contain at least one feature it is explaining.

An attachment report carries its source bundle. A revision report contains its earlier draft. A font-mapping report lets you copy out the alternate reading.

## The three I would promote immediately

| Priority | Source | Why |
|---|---|---|
| 1 | `thoppe/PDF_steganography` | Small enough to understand completely; direct artistic potential |
| 2 | Asymptote + the interactive example | Introduces a genuinely different medium: geometry rather than pages alone |
| 3 | `pdfv3dReader` | Opens the question “what if we build another interpreter?” rather than only testing existing ones |

Keep `pdf_hide` and PDFStego as contrasting specimens about hidden information. Keep Bad Apple as a playback implementation to dissect, pending full source inspection.

The strongest new direction is not another game port. It is this: make a document with several intentional readings, then build the tools that let someone discover how each reading is produced.
