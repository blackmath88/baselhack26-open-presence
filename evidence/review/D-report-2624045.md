## Verified findings

### B1 — BLOCKER: legacy review routes defeat the Commons transaction and allow contradictory successful decisions

Evidence: `apps/commons/server/http/api.ts:216–231` calls `services.curation.accept/reject` directly. `server/container.ts:74–80` wires those services to the outer repository, rather than its transaction view. `server/application/curation-service.ts:42–44` reads and validates first and appends later (`:106`, `:123–134`). The JSON queue serializes individual reads/appends (`server/persistence/json-repository.ts:61–65`), not that complete legacy operation. The live UI uses this route: `src/state/useRoom.ts:263`, `src/lib/api.ts:143–146`.

Reproduction: scratch `reproduce.mts` ran a real HTTP server bound to 127.0.0.1:8799, using the real JSON repository and imported pinned records. Concurrent requests to legacy `/api/curation/commons%3Aemmc-not-exposed%3Arelation%3A0/accept` and `/api/commons/reviews` with decision reject **both returned 200**. Persisted tail was `RelationRejected`, then `RelationAccepted`; final proposal was accepted and one canonical relation existed. See `reproduction-results.json` and `repro-events.json`. No scheduler mocks or forced barriers were used.

Failure scenario: two participants review the same connection through the UI/API concurrently; one sees a successful rejection while stale validation permits another acceptance. The later append silently wins projection status. This violates the explicit G4 conflict rule. Legacy contribution submission (`http/api.ts:192–211`, `application/contribution-service.ts:82–85,118–119,133–138`) likewise reads state outside a full transaction and generates proposals from a potentially stale state; that contribution-specific race consequence is a code-reading hypothesis, not separately reproduced.

Repair: put complete validation-plus-event generation for every writer on the same serialized transaction boundary, including legacy routes (or reject Commons IDs on legacy writers and migrate the UI). Add mixed-route and UI-route concurrency acceptance coverage, not only Commons-versus-Commons tests.

Existing pinned records remain immutable, and the current static Finder does not display these injected records.

Failure scenario: a normal participant calls the exposed import endpoint with fabricated source material and the API stores/returns it as imported Postack source provenance rather than an untrusted participant assertion. This is not a reproduced XSS: Finder rejects non-GitHub links and uses escaped text. Restrict pinned corpus import to trusted startup/admin code, or enforce a trusted corpus identity and explicit untrusted-import qualification; validate the full contract.

## Notes and limits (not reproduced corruption/exploitation)

### N1 — NOTE: atomic document replacement does not establish power-loss durability

`server/persistence/json-repository.ts:46–55` writes events and receipts into one temp document and renames it, with no file/directory fsync. **Code-reading limitation:** process-crash split-brain between event append and command receipt is avoided because both remain in memory until the one replacement; there are not separate event and receipt disk writes. A host power failure after an acknowledged write can still lose the latest replacement depending on filesystem behavior. No power-failure or kill-at-write experiment was performed. The implementation explicitly supports a single process (`:13–14`); cross-process exclusion is outside that stated guarantee.
