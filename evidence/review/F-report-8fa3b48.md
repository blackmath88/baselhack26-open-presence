## Verified SHOULD-FIX

### F-S1 — wrapper drops the supplied room and can review a different room's proposal

**Verified service-level and real MCP transport regression.** `server/container.ts:93–97` uses `input.problemId` only for the `commons:` prefix switch, then omits it from the command. `server/commons/service.ts:84–87,96–97` searches all proposal events and selects the proposal's actual room. It never checks that the caller's supplied room exists or matches.

Reproduction: call `review_curation_proposal` with `problemId: "commons:no-such-room"`, `proposalId: "commons:emmc-not-exposed:relation:0"`, `accept: false`, and a rationale. The real SDK client receives a successful result and a `RelationRejected` event is persisted in **commons:emmc-not-exposed**, despite requesting a nonexistent room. Immediately before that call, the unwrapped generic curation service on the same repository and actor rejects the same room/proposal pair with `not_found: Problem not found` (`server/application/curation-service.ts:29–32`). A second direct-wrapper reproduction also succeeds for relation 1 under a nonexistent room. See `mcp-probe.mts`, `mcp-probe-results.json`, `mcp-probe-events-final.json`, and `probe-results.json`.

This is a room-target correctness defect, not a demonstrated privilege escalation: current review authorization is global scope plus independent-review policy, rather than room membership. A stale/mismatched client request can nevertheless perform a real human-attributed review in a room it did not name. The MCP regression is introduced by batch 3; the analogous HTTP bridge already omitted room in batch 2.

Repair: carry an expected room through the serialized review command and validate its existence and proposal membership inside the same transaction. Preserve idempotency and return a domain error without appending for mismatched/nonexistent rooms. Do not reintroduce a separate outside-transaction validation step.

## Notes and hypotheses

### F-N1 — compatibility projection is not scoped to imports

**Verified synthetic projection behavior; production reachability unproved.** `server/domain/projections.ts:90` changes every ContributionAdded kind `observation` into evidence, without inspecting room ID, import actor or provenance. `probe.mts` projects a non-Commons room with `person:kai` / `source: direct` observation events and gets evidence contributions (`probe-results.json`, `nonImportObservation`). Thus a non-import legacy observation can be misclassified. Current public add/edit validation rejects observation because it is not in CONTRIBUTION_KINDS, so no supported current HTTP submission creates such an event. Narrow the rule to the known imported provenance if broader legacy stores must be preserved; no ordinary current-user corruption was reproduced. ContributionEdited kind is unchanged by this normalization.

### F-N2 — optional reason validation differs across interfaces; no shared length bound

**Verified.** Direct Commons review rejects explicit empty and whitespace-only reasons (`server/commons/service.ts:16–19,94`). HTTP optionalStr likewise rejects them (`server/http/api.ts:74–81`). MCP's schema permits empty strings and its adapter/wrapper truthiness checks discard them (`server/mcp/register-tools.ts:332,345`; `server/container.ts:97`), so an empty MCP reason succeeds as absent; whitespace reaches Commons and fails invalid. MCP rejects 1001 characters at schema validation. Commons service accepts and persists 1001- and 100001-character reasons; HTTP has only the overall 16 MiB request ceiling, rather than a reason-specific cap. See `probe-results.json` and the corrected final `mcp-probe-results.json` (each test uses an existing fresh proposal).

The frozen ReviewCommand defines optional string reason and no maximum, so this is a consistency/resource-bound recommendation rather than a failed explicit maximum-length requirement. Define one optional-string normalization and length policy at the shared boundary, including receipt hashing. Valid nonempty reasons and changed-reason retry conflicts work.

### F-N3 — enriched curation reads duplicate full repository work

**Code-reading performance concern; no load failure or latency regression reproduced.** `server/http/api.ts:169` first loads/projects the room through generic curation, then `:172` calls getRoom, which enters the shared transaction queue, reloads the JSON document and constructs full history, source, contribution and relation projections (`server/commons/service.ts:112–125`). JSON persistence loads/parses the whole document and serializes it to detect changes even for this transaction read (`server/persistence/json-repository.ts:46–58`). The endpoint needs a small subset of that result. This adds duplicate projection/allocation and queues reads with writers as the log grows. Prefer one enriched snapshot/read operation if scaling beyond the small local corpus; no benchmark-based performance claim is made.
